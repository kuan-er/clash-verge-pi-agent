# Plan: Chain-proxy auto-selection and simplified subscriptions

## Goal
For chains defined in the active YAML, hold the manually chosen exit fixed, measure each transit candidate **directly against the `/204` HTTP service on the exit server** without changing the live transit, and select the fastest reachable transit every five minutes; retain a manual measure-and-update action. After verifying that behavior, hide the proxy UI; defer authenticated subscriptions until the login API is specified.

## Background
- `src/components/home/current-proxy-card.tsx` already performs optional periodic **current-node-only** delay checks (default five minutes) and has a manual **measure-all-only** button. Neither selects the fastest transit node; the timer belongs to a Home card, so it may stop when the page unmounts.
- `src/services/delay.ts` provides node delay measurements and defaults to `http://cp.cloudflare.com/generate_204`; selection is centralized in `src/hooks/use-proxy-selection.ts`. `src-tauri/src/config/runtime.rs` and `src-tauri/src/cmd/runtime.rs` handle `dialer-proxy` chains; the runtime chain editor may overwrite YAML-provided links.
- `src/pages/_navigation.tsx` declares the proxy page. The Home card links to `/proxies`, and other navigation references may exist.
- `src/pages/profiles.tsx` and `src/components/profile/profile-viewer.tsx` accept local files and arbitrary remote URLs. Rust `src-tauri/src/config/prfitem.rs` and `src-tauri/src/feat/profile.rs` own remote fetching and updates; existing profile types include script/merge for internal enhancement.
- Repository `AGENTS.md` requires a pre-existing issue or maintainer approval for nontrivial work, scoped changes, justified tests, English code/commits, and Conventional Commit subjects.

## Steps
1. **Fix specification using documented mihomo semantics.** User approved this task as the repository's nontrivial-change authorization. The user will manually choose an exit (currently only one), while the program changes only the transit hop. Mihomo's `dialer-proxy` may name a `select` group; its members are transit candidates. The user chose an HTTP `/204` service hosted directly **on the exit server** as the probe target: measure each transit's reachability/latency to that service, **not** the strict full proxy-to-destination path, and **do not** switch the live transit for each probe. Official docs: https://wiki.metacubex.one/en/config/proxies/dialer-proxy/ , https://wiki.metacubex.one/en/config/proxy-groups/ and https://wiki.metacubex.one/en/api/ . Discover the exit and transit group from active effective YAML (`dialer-proxy` link); use the actual exit-service URL configured in the YAML group's `url` if present, otherwise require an explicitly configured URL rather than silently probing Cloudflare. Do not infer the HTTP port, TLS scheme, or public hostname from the exit proxy server address.
2. **Implement and verify chain selection first.** For every candidate in the transit selector, call the core's **per-proxy delay test** with the exit server's `/204` URL (and expected HTTP status 204 if supported by the API); do not probe the exit proxy or change the transit selector during measurement. Compare valid finite latencies, select the fastest reachable candidate once after the batch, and leave the current selection unchanged when all fail. Guard against concurrent runs, changing profile/core, or changing exit selection; avoid unintended persistence of temporary state (no temporary selection is required). Start with a manual measure-and-update action on Home to verify the mechanism; then wire a five-minute scheduler that works independently of which page is open and stays enabled regardless of the optional current-node-delay toggle (and when the window is closed but the app/core stays active if lifecycle supports it). Keep manual trigger accessible and use the same engine. Add narrowly targeted tests for candidate discovery, timeout/all-fail behavior and selection; run `pnpm test` (or targeted suite), `pnpm typecheck`, `pnpm lint`, and applicable Rust checks. Confirm with a local YAML and running core including restart, profile switch, failures, and repeat interval; commit this part with a scoped Conventional Commit subject.
3. **Hide proxy UI only after step 2 works.** Remove its sidebar entry and Home navigation/link, but keep the `/proxies` route available for direct access (UI-only hiding). Keep the new manual control on Home. Run UI checks and smoke-test selection; commit separately.
4. **Subscriptions: defer remote login implementation until contract exists.** Local YAML import stays available. Once endpoint, query names, credential handling, and refresh semantics are agreed, replace user-facing arbitrary URL creation with login; retain internal script/merge types. Backend-mediated HTTPS GET must not log credentials or persist full URLs containing them. Validate YAML via the existing pipeline and check login/import/refresh. Test and commit as a separate third part; do not invent a login implementation before the interface is known.

## Risks & Open Questions
- **Approved:** User explicitly approves this task in lieu of an issue; still comply with repository requirements for scoped diffs, English code/commits, and Conventional Commit subjects.
- **Chain discovery:** Which YAML shape is actually used in deployment (especially if it uses direct `dialer-proxy: node` links instead of `dialer-proxy: selector`)? Without a representative YAML, implement the documented selector-group pattern only and report unsupported shapes rather than silently changing topology.
- **Probe design agreed:** User selected the exit-hosted `/204` service for testing each transit candidate without switching the live selector. This approximates the best end-to-end chain based on latency to the exit host, but omits exit-proxy handshake and exit-to-final-destination latency; do not describe it as an exact full-chain measurement. Use per-proxy core delay API (or `/group/{name}/delay` if its semantics match) with HTTP 204 validation; `url-test` supports `url`, `interval: 300`, `lazy: false`, and `expected-status: 204` according to official docs: https://wiki.metacubex.one/en/config/proxy-groups/url-test/ and https://wiki.metacubex.one/en/config/proxy-groups/ .
- **Configuration prerequisite:** the full reachable URL, e.g. `http://exit.example:8080/204` or `https://exit.example/204`, must be available in YAML or user configuration; the exit proxy's server/port does not determine the `/204` endpoint. Make missing URL actionable rather than falling back to an unrelated target.
- The desired end-to-end probe may temporarily route traffic through each candidate. Need to validate that the core applies switching before each probe and that changes to an exit node's selection mid-cycle are handled safely.
- **UI-only hiding:** `/proxies` remains directly reachable; navigation is removed.
- **Deferred third part:** Login API endpoint/parameters, password storage and refresh strategy, and migration of existing URL subscriptions remain unknown. Do not present a mocked login as working.
- End-to-end availability cannot be claimed from static checks alone: a real YAML, core process, and reachable test endpoint are required.

## Design Decisions
- **End-to-end approximation:** Probe each transit directly against the exit-hosted `/204` service without changing the live transit; this ranks the transit-to-exit-server paths, not the exit-to-destination portion of the full chain.
- **Phased commits:** implement, test, and commit the working manual/automatic chain feature first, then hide the proxy UI; handle authenticated subscription separately when its API is known.
- **Runtime ownership:** avoid placing the only five-minute scheduler on a page component that can unmount.
- **Credential boundary:** use backend HTTP handling and explicit authentication configuration rather than embedding account/password in an ordinary remote subscription URL.
- **Scope:** retain internal profile types required by the YAML enhancement pipeline; limit the restriction to user-facing subscription methods unless product requirements explicitly say otherwise.
